# ADR-010: Publish the packages to public npm via trusted publishing, on a version tag

## Status

Accepted — 2026-09-24. Lineage: sii ADR-015 (tag-triggered CD), ADR-019 (public
npm, personal scope), ADR-021 (surfaces published in lockstep); hardened here.

## Context

ADR-002 names three packages that move in lockstep, and ADR-004 makes the repo a
public MIT release, but nothing decides how the packages reach users. sii solved
it with a `v*`-tag workflow that publishes with a long-lived `NPM_TOKEN` and then
creates a GitHub release from `CHANGELOG.md`. `cta` reads bank accounts, so a
compromised package is worse than in sii: supply-chain integrity weighs more.
Deciding now lets the workflow and package metadata land before the first
useful release, instead of being improvised at release time.

## Decision

- **Registry and scope:** public npm, `@albertomarturelo/cta-core`, `-cli`, `-mcp`
  (lineage: sii ADR-019). `publishConfig: { access: public }`; each package ships
  `dist`, `README.md` and `LICENSE`.
- **Lockstep, tag-triggered:** all three `package.json` carry the same version;
  merging the bump and pushing tag `v<version>` is the only way to release
  (lineage: sii ADR-015/021). The workflow fails if any version differs from the tag.
- **Trusted publishing (OIDC), no `NPM_TOKEN`:** each package on npmjs.com trusts
  `albertomarturelo/cta` → `.github/workflows/publish.yml`. The publish job has
  `id-token: write`; npm issues a short-lived credential and attaches
  **provenance** (the package is linked to the commit and workflow that built it).
  No publish secret exists in the repo.
- **Mechanism:** `pnpm pack` per package (rewrites `workspace:*` to the real
  version), then `npm publish <tarball>` with an npm CLI that supports trusted
  publishing. Idempotent: a version already on npm is skipped, not an error.
- **Gate before publish:** the publish job runs install (frozen), `pnpm typecheck`,
  `pnpm lint`, `pnpm test` and the tag check — sii only built.
- **Least privilege:** the publish job has `contents: read` + `id-token: write`
  only. A separate `release` job, run only after publish succeeds, has
  `contents: write` and creates the GitHub release with notes lifted verbatim from
  the version's section of root `CHANGELOG.md` (lineage: sii publish workflow);
  missing section → autogenerated notes plus a warning. Idempotent.
- **Bootstrap:** if npm requires a package to exist before a trusted publisher can
  be attached, the owner publishes each package's first version once, locally,
  with npm 2FA. From then on only CI publishes.
- **When:** the workflow and metadata land now and stay inert until a tag is
  pushed. The first tag waits for a useful surface: at least `cta saldo` working
  against one bank.
- **Release notes are public artifacts:** `CHANGELOG.md` follows ADR-009 like any
  tracked file — no account data, no personal facts.

## Alternatives Considered

1. **Long-lived `NPM_TOKEN` secret, as in sii.** Rejected — a leaked automation
   token publishes anything under the scope until revoked, and it yields no
   provenance. OIDC removes the secret entirely.
2. **`pnpm -r publish` directly (sii).** Rejected as the publish step: trusted
   publishing is implemented by the npm CLI; `pnpm pack` + `npm publish` keeps the
   `workspace:*` rewrite and gets OIDC. Revisit if pnpm supports OIDC natively.
3. **No npm release; install from git or source.** Rejected — `npx`/global install
   is how an MCP client and a CLI user actually consume the tool; building from
   source is a barrier.
4. **Release automation (changesets, semantic-release).** Rejected at three
   lockstep packages and one maintainer: a hand-written `CHANGELOG.md` section plus
   a tag is enough, and the curated text is what users read.

## Consequences

- Easier: a release is "bump, changelog, merge, tag"; users can verify on npm that
  a version came from this repo's CI.
- Obligation: configure the trusted publisher per package on npmjs.com; keep the
  three versions equal; write the `CHANGELOG.md` section before tagging.
- Risk: npm's trusted-publishing requirements (CLI version, first publish) may
  change; the workflow step documents the version it relies on.
